## 1. 总体印象与“像不像宁波博物馆”

### 1.1 总体评分：**6.8 / 10 分**

### 1.2 审美与风格总评
场景成功营造出了一个清新、温润、具备可读性的江南水乡卡通画卷。Three.js 的轻量化程序化资产配合无外链单文件交付，在极小体积（683 KB）下塞入了完整的昼夜变换、湖面反射倒影、风吹草动和游客动态，工程装配完成度较高。

### 1.3 建筑还原度评价：“像”在哪里？“假”在哪里？

#### 成功捕捉的特征（“像”）：
1. **山体拓扑意向准确**：西端贯穿进深的 28m 大裂口、南侧 14m 宽的“山谷”大台阶，以及自三层起劈裂出的 5 个山头状体量，高度在 16m~24m 之间跌宕起伏，正确还原了王澍作品“人工山体”的母题。
2. **直斜分段与材质分区准确**：底层 10.5m 直壁采用瓦爿墙，上部内收约 6.5° 的斜壁采用竹模清水混凝土，屋顶铺设灰青筒瓦，建筑上下“实与虚、重与拙”的对立统一关系成立。
3. **地域水系与古堰还原**：引入了宁波标志性的古代水利工程“它山堰”作为跨越水面的主引道，木桩列、跌水石级和亲水芦苇形成了强烈的宁波在地感。

#### 致命的失真与破绽（“一眼假”）：
1. **瓦爿墙贴图呈明显机械拼贴感（壁纸瓷砖感）**：
   - 瓦爿墙的核心在于明清旧砖瓦手工干砌的“乱石穿空”与不可预测性。
   - 当前贴图尺寸仅 3.0m × 3.0m，在长达 144m 的立面上横向机械重复了 **48 次**！贴图中的红色拱形龙骨砖与深灰瓦条像网格状图案一样均匀布满整个墙体，完全失去了王澍建筑中那股源自拆迁瓦砾堆的厚重与沧桑。
2. **南面“山谷大台阶”通透漏风，失却《溪山行旅图》正观气象**：
   - 实景中的南面大台阶是《溪山行旅图》式的内聚型峡谷，沿台阶而上进入的是深邃的内院平台。
   - 本场景中大台阶正对尽端（`05-valley.png`）的两个体量彻底向后敞开，台阶尽端没有任何空间封堵，直接漏出北侧蓝天、远山甚至城市高楼方块，使整个大台阶沦为一个两端透光的“穿堂过道”。
3. **百叶窗与斜壁开窗扁平如纸，且叶片完全埋入墙内**：
   - 百叶窗在近看（`09-closeup-wall.png`）时仅为一个浅灰框，框内没有任何叶片纹理（因坐标偏移符号错误全部嵌进混凝土内部）；
   - 斜壁上的横向长窗呈现为刺眼的高反光纯蓝贴纸，缺乏王澍作品中厚墙开洞（城堡深凹窗洞）所具有的阴影进深与神秘感。
4. **垂直落水管像囚笼铁栏，且与水平线脚生硬穿模**：
   - 瓦爿墙每隔 16m 设置了一根从顶贯底的深灰圆柱，在透视下像一组铁栅栏；且直接垂直穿透三道凸出的水平花岗岩腰线，毫无建筑交接构造。
5. **场地边缘“刀切”悬空，孤立于荒原之上**：
   - 航拍视角（`06-aerial.png`）下，北广场的矩形铺装地砖与周边草坪呈现绝对的 90° 几何硬切边界，没有任何市政道路接驳，像一张悬浮的地毯。

## 3. 代码与实现问题清单

### C1（P0 · 运行时致命错误 & 道具丢失）：`src/props.js:726` 传参错误导致垃圾桶未生成并抛出控制台异常
- **file:line**：`src/props.js:726`
- **问题代码**：
  ```javascript
  add(mergeGeos(bins), toonMat({ color: 0x4b5257 }));
  ```
- **为什么是问题**：在 `src/props.js:27` 中，`add` 定义为接收单个 Object3D 参数：
  ```javascript
  const add = (m) => { group.add(m); return m; };
  ```
  但在第 726 行，作者却传入了 `BufferGeometry` 和 `Material` 两个参数。这导致代码直接将 `BufferGeometry` 传入 `group.add(geometry)`，抛出运行期错误：
  `THREE.Object3D.add: object not an instance of THREE.Object3D.`
- **影响**：
  1. 浏览器控制台常驻报错；
  2. 场景中所有的垃圾桶（`bins`）未能实例化为 Mesh，**全场景垃圾桶 100% 丢失**。
- **建议改法**：
  ```javascript
  add(meshOf(mergeGeos(bins), toonMat({ color: 0x4b5257 })));
  ```

### C2（P0 · 几何逻辑错误）：`src/museum.js:576` 偏移符号反转导致斜壁百叶叶片埋入墙内
- **file:line**：`src/museum.js:575-576`
- **问题代码**：
  ```javascript
  const sl = faceAttach(boxG(2.2, 0.12, 0.18, 0, 0, 0), y - 0.36 + i * 0.18, sgn);
  sl.translate(x, y - 0.36 + i * 0.18, zz - sgn * 0.06);
  louv.push(sl);
  ```
- **为什么是问题**：
  在北立面，`sgn = -1`，墙面外表面坐标为 `zz`。外框（line 573）位于 `zz + sgn * 0.03 = zz - 0.03`（向北，在墙外）。而叶片被平移到 `zz - sgn * 0.06 = zz + 0.06`（向南，深入墙体内侧 6cm），直接被 0.85m 厚的斜壁实体整体吞没。
- **影响**：北立面百叶叶片全部看不见，变成空框，出现严重穿模遮挡缺陷（见缺陷 V1）。
- **建议改法**：
  ```javascript
  sl.translate(x, y - 0.36 + i * 0.18, zz + sgn * 0.06);
  ```

### C5（P1 · 运行期性能开销）：`src/main.js:190-194` 每帧垃圾回收对象分配
- **file:line**：`src/main.js:190-194`
- **问题代码**：
  ```javascript
  function updateLights(st) {
    ...
    const dir = camera.position.clone().sub(controls.target).normalize();
    fill.position.copy(controls.target).add(dir.multiplyScalar(130)).add(V3(0, 70, 0));
  ```

- **为什么是问题**：
  在主渲染循环 `frame()` 中，每一帧都调用 `applyDay(st)` -> `updateLights(st)`。第 190 行的 `.clone()` 每帧分配新的 `Vector3` 对象，60fps 下每秒产生几百个垃圾对象，诱发垃圾回收（GC）微卡顿。

### C6（P2 · 隐式对称假设）：`src/water.js:181` 涟漪环位置坐标硬编码
- **file:line**：`src/water.js:181`
- **问题代码**：
  ```javascript
  r.position.set(x, WATER_Y + 0.02, L.weir.z1 * sgn + 1.5 * sgn);
  ```
- **为什么是问题**：
  当 `sgn = -1` 时，位置计算为 `-L.weir.z1 - 1.5`。这里隐式假设了 `L.weir.z0 === -L.weir.z1`。虽然目前 `z0 = -6.6, z1 = 6.6`，但若未来重构调整了非对称堰宽，南侧涟漪位置将发生隐蔽漂移。
- **建议改法**：
  ```javascript
  r.position.set(x, WATER_Y + 0.02, (sgn > 0 ? L.weir.z1 : L.weir.z0) + 1.5 * sgn);
  ```

### C7（P2 · 相机克隆属性同步风险）：`src/post.js:122` 描边法线相机同步不完全
- **file:line**：`src/post.js:122`, `140-144`
- **问题代码**：
  ```javascript
  normalCam.position.copy(camera.position);
  normalCam.quaternion.copy(camera.quaternion);
  normalCam.projectionMatrix.copy(camera.projectionMatrix);
  normalCam.projectionMatrixInverse.copy(camera.projectionMatrixInverse);
  normalCam.near = camera.near; normalCam.far = camera.far;
  ```
- **为什么是问题**：手工拷贝相机矩阵和属性。若主相机动态调整了 `fov`、`zoom`、`view` 等视口属性，未执行 `normalCam.copy(camera)` 容易造成法线通道渲染视锥体错位。
- **建议改法**：直接调用 `normalCam.copy(camera);`。

### 可优化项与预估收益：
1. **防抖动态 PMREM 生成**（预估收益：消除滑块卡顿）：
   - `src/main.js:205` 在时刻变化大于 0.4h 时会同步生成 64×32 Canvas 并调用 `pmrem.fromEquirectangular`。快速拖动滑块时会发生密集的 GPU 纹理重建。
   - **优化方案**：在滑块拖动事件中对 `refreshEnv` 进行 100ms 防抖，拖动过程中仅插值环境光，松手后生成 HDR PMREM。
2. **材质合并与顶点色利用**（预估收益：材质数由 142 降至 40，显存程序编译减少 40%）：
   - 将石凳、长椅、道牙等同类型单一色块对象统一合并，并以顶点色刷色，复用统一的全局材质实例。

## 8. 不确定 / 需要用户决策的点

1. **南面大台阶顶端的封堵程度**：
   - 实景中大台阶登顶后是二层开放平台和内院，若完全封死可能影响从台阶登顶进入二层的视觉通畅度；若不封死则会导致当前的“穿堂漏风”。需要用户决策是倾向于“封闭型山谷深邃感”还是“开敞型平台通透感”。
2. **瓦爿墙贴图精度与文件体积的权衡**：
   - 若引入 2~3 张不同种子的 1024px 贴图打散重复感，或者将瓦爿贴图提升至 2048px，单文件 HTML 大小可能会增加 200~300 KB（由当前的 680 KB 增至约 900 KB~1MB）。需由用户决策对文件体积与贴图质量的优先权。
3. **卡通描边（Outline）默认开关状态**：
   - 目前送审版本默认关闭描边（`state.outline = false`）。描边开启时更具国漫写意风格，但会增加 1 次全屏法线渲染通道并在部分斜壁边缘产生细微断线。需由用户确认默认是主打“精致赛璐璐描边”还是主打“纯三维写意光影”。
